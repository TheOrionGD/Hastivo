1.  Product Overview

The product is an interactive, AI-assisted sign-language communication
platform. It is intended to help people communicate across
spoken/written language and sign language through two primary
translation directions: Text-to-Sign and Sign-to-Text. It also provides
a real-time, two-participant conversation experience that combines
speech capture, sign recognition, contextual language processing, speech
output, and an animated 3D avatar.

The platform is more than a text translator or a camera-based gesture
demo. It is a multi-service application combining a user-facing web
experience, secure application backend, language/AI processing, computer
vision, sign representation, avatar animation, real-time event delivery,
persistence, moderation, and administration.

1.1 Primary capabilities

Introduce the product through an animated splash experience and exactly
seven onboarding screens.

Provide public landing, registration, login, and authenticated user
experiences.

Convert typed text or speech transcripts into structured sign sequences
and play them through a 3D avatar.

Recognize sign-language input from a live camera stream, display
recognized signs, and produce a contextual sentence.

Convert generated text to speech with user-configurable voice and
playback settings where supported.

Support simultaneous speech-to-sign and sign-to-speech/sign-to-text
workflows in a real-time conversation session.

Persist user-owned translation and conversation history.

Provide user settings, profile management, moderation review,
administrator actions, notifications, and audit trails.

1.2 Language and accuracy principles

Sign languages are complete natural languages with their own grammar,
word order, non-manual markers, spatial features, and regional
variation. The system must not assume that a spoken-language sentence
can be translated by replacing each word with an isolated gesture. Nor
may it assume that a model trained for one sign language works for
another. The target sign language, supported dialects, dataset
provenance, vocabulary coverage, and evaluation methodology must be
explicitly selected and documented.

The requirements supplied so far do not conclusively lock the target
sign language. Given the intended context, Indian Sign Language (ISL)
may be a candidate, but the implementation agent must confirm this
product decision with the owner before selecting datasets or claiming
language coverage. ASL, ISL, and other sign languages are not
interchangeable.

2.  Product Principles and Non-Negotiable Rules

Functional correctness takes priority over visual completeness.

Use real persisted data and actual service responses in production
workflows.

Never show dummy values, fabricated analytics, random recognition
labels, or hardcoded AI outputs as genuine results.

Do not delete unused declarations or incomplete functions merely to
silence lint diagnostics; investigate and implement their intended
behavior.

Do not disable lint rules, suppress compiler diagnostics globally, or
weaken tests to manufacture a clean report.

Do not create disconnected services, duplicate business logic, or
unnecessary microservices.

Every visible control must perform its advertised action or be clearly
disabled/unavailable.

All errors, unavailable dependencies, permission failures, and
low-confidence recognition outcomes must be represented honestly.

Protect user privacy, especially camera, microphone, biometric-like
landmark, and conversation data.

4.8 Text-to-Sign workspace

Purpose: convert user-provided text or speech transcript into a
linguistically valid sign sequence and render that sequence using the 3D
avatar.

Inputs

Manual text entry.

Speech input through browser/device speech recognition or a configured
speech-to-text provider.

Editable transcript before translation.

Explicit source-language and target-sign-language selection where
supported.

Processing and output

Validate and normalize the input while preserving the user’s intended
meaning.

Identify the source language when supported.

Perform context-aware linguistic processing; do not use naive
word-by-word substitution.

Map the processed meaning into a supported sign-language representation,
such as gloss/structured sign tokens and required non-manual or spatial
metadata where the language model supports them.

Resolve each sign token to a validated animation asset or procedural
animation instruction.

Return an ordered sequence with timing, transitions, metadata, and
confidence/coverage information where available.

Render the sequence through the 3D avatar.

Provide play, pause, resume, replay, speed adjustment, and relevant
synchronization controls.

Allow the user to inspect the input and translation output.

The avatar must not pretend to sign unsupported vocabulary. If a sign is
unavailable, report the uncovered segment and offer a clear limitation
state rather than silently substituting an unrelated gesture. This page
has no footer.

4.9 Sign-to-Text workspace

Purpose: capture sign-language activity through a live camera, recognize
supported signs, and convert the recognized sequence into readable text.

Request camera permission only when the user initiates the camera
workflow.

Display a large landscape-oriented camera workspace, approximately 16:9
where screen size permits.

The original requirement mentions a six-metre line/reference. Treat this
as a capture-distance or calibration requirement to be clarified and
validated, not as a guaranteed distance measurable by an ordinary
webcam.

Overlay hand/body landmarks, joints, connecting lines, motion trails,
and recognition indicators where available.

Recognize signs using an actual trained model and supported dataset.

Display recognized words/sign tokens sequentially with timestamps and
confidence where available.

Preserve the raw recognized sequence separately from the AI-generated
sentence.

Use contextual language processing to generate a readable sentence
without changing the intended meaning or adding unrelated content.

Provide optional text-to-speech playback with supported voice choices,
speed, and volume controls.

Release camera and processing resources when the user stops or leaves
the workspace.

Do not claim reliable recognition outside the trained dataset, camera
conditions, signer variation, and evaluated vocabulary. This page has no
footer.

4.10 Conversation History

Provide searchable, filterable, user-scoped records for:

Text-to-Sign: original text/transcript, language settings, generated
sign sequence metadata, and replayable animation references.

Sign-to-Text: recognized sign sequence, generated sentence,
confidence/coverage information, and speech metadata.

Text-to-Speech records where the product chooses to persist them.

Real-Time Conversation: session participants, timestamped
messages/events, and session metadata.

Support search, category/date filters, detail view, replay where assets
remain available, individual or selected deletion, and export where
implemented. Use chronological lists/timelines and dividers rather than
generic cards. Enforce ownership and retention rules.

4.11 Real-Time Conversation

Provide a simultaneous two-participant workspace. On wide screens, use
two coordinated columns; on smaller screens, stack the workspaces while
preserving clear participant identity.

Participant A — speech to sign

Speech input only in this module; do not add manual typing as the
primary input for this participant.

Capture speech and produce a live transcript.

Send transcript for contextual AI processing.

Convert the result into sign-language sequence instructions.

Play the sequence through the 3D avatar.

Show transcript, processing status, current sign, and playback controls.

Participant B — sign to text/speech

Capture sign input through the camera.

Run landmark tracking and actual sign recognition.

Display recognized words sequentially.

Process the recognized sequence into a contextual sentence.

Display both raw recognized words and the generated sentence.

Optionally speak the generated sentence using configured TTS settings.

Session behavior

Support Start, Stop, Pause, Resume, and Continue controls with clearly
defined state transitions.

Continue should finalize/process the participant’s current input and
make the resulting output available without ending the overall session.

Stop should stop the relevant capture/processing operation or end the
session according to the control context; the UI must make the scope
clear.

The two participant pipelines must run independently and must not
unnecessarily block one another.

Preserve message order, participant association, and timestamps.

Handle reconnects, permission loss, service failures, and participant
disconnection.

Persist completed sessions and associated records in History according
to user consent and retention settings.

10. AI and Sign-Language Processing Specifications

10.1 Text-to-Sign pipeline

Receive validated text or a speech transcript from the backend.

Identify source language and normalize text without losing meaning.

Perform contextual and semantic analysis.

Apply target sign-language grammar and representation rules.

Produce a structured sign sequence (for example, gloss/token sequence
plus supported spatial, timing, and non-manual metadata).

Resolve tokens against a versioned sign vocabulary and animation
library.

Return sequence metadata, unsupported-token coverage, confidence where
meaningful, and model/dataset version.

The frontend avatar renderer executes the validated sequence and exposes
playback controls.

10.2 Sign-to-Text pipeline

Acquire permitted live camera frames.

Detect hands and relevant body/face landmarks.

Extract temporal features across frames, not only isolated still-image
poses.

Run the configured sign recognition model.

Produce recognized tokens with timestamps and calibrated confidence
where available.

Apply language-aware sequence processing to generate a sentence.

Return raw recognition and generated sentence as separate fields.

Offer optional TTS and persist the result according to user settings.

10.3 Model and dataset governance

Record model name/version, dataset source/version, license,
language/dialect, vocabulary scope, and preprocessing assumptions.

Document training, validation, and test separation to prevent data
leakage.

Measure accuracy using suitable metrics and representative
signer/device/lighting conditions.

Calibrate confidence thresholds and define low-confidence behavior.

Do not state that the system understands all sign language or supports
unrestricted conversation unless demonstrated by evaluation.

Provide a clear unsupported-sign or uncertain-recognition path.

12. Moderation and Administration

Moderate manual text, speech transcripts, AI-generated sentences,
sign-recognized content, and real-time conversation content where policy
and privacy permit.

Create a moderation record with category, severity, confidence,
timestamp, user/session reference, evidence reference, and review
status.

Treat automated detection as a signal for human review, not conclusive
proof.

Provide administrators with a review queue and relevant context subject
to role permissions.

Allow authorized administrators to apply a 24-hour temporary block or a
7-day temporary suspension after review.

Restrictions must store start and expiry timestamps, block
login/protected access during the period, and automatically expire
unless extended.

Do not delete the user’s account when applying a temporary restriction.

Send an email notification through a configured provider with reason,
restriction type, start/end, and appeal/review information.

Record administrator identity, decision, reason, timestamps, and changes
in an append-only or tamper-evident audit trail where feasible.

Define appeal handling, moderation retention, notification retries, and
administrator permission scopes before production release.

13. Security, Privacy and Accessibility

Use HTTPS/TLS in deployed environments and secure cookie/token practices
appropriate to the chosen authentication design.

Hash passwords with a modern password-hashing algorithm such as
Argon2id; never store plaintext passwords.

Enforce server-side authorization on every protected resource and
administrative action.

Validate and sanitize inputs; apply rate limits, secure headers,
appropriate CORS, and abuse protections.

Keep secrets in environment/secret management, never in source code or
frontend bundles.

Request camera and microphone permissions only when needed and explain
their purpose.

Provide clear recording/processing indicators and stop controls.

Do not persist raw video/audio unless explicitly required, consented to,
and covered by retention controls.

Minimize personal data, restrict access, and support deletion/retention
policies.

Support keyboard navigation, semantic controls, visible focus,
screen-reader labels, contrast, captions, and reduced motion.

14. Zero Placeholder / Zero Fake Data Policy

Production behavior must never rely on fabricated content presented as
genuine.

No dummy users, profiles, emails, phone numbers, conversation messages,
history records, dashboard metrics, moderation alerts, or notifications.

No hardcoded AI outputs, random sign labels, fabricated confidence
values, generated landmark coordinates, or simulated model success.

No fake API responses or artificial delays that imitate real processing.

All dynamic data must come from its actual service/database/model.

Use genuine empty states (for example, zero counts and ‘No activity
yet’) when no records exist.

If a dependency is unavailable, return a structured unavailable/error
response and show a truthful UI state.

Static constants are allowed for configuration, design tokens, route
identifiers, supported language lists, and other genuine application
constants.

Mocks and fixtures are permitted only in isolated tests or clearly
separated showcase demonstrations; they must never enter production
workflows or be represented as real results.

15. Code Quality and Lint Remediation Policy

Run the correct lint, type-check, compiler, and test tools across every
service. Investigate every diagnostic rather than suppressing it.

Identify unused variables, imports, parameters, functions, components,
hooks, types, state, service methods, API endpoints, and configuration.

For each unused declaration, trace its intended purpose through
references, requirements, API contracts, and workflows.

If it represents unfinished functionality, implement and connect that
functionality; do not delete it merely to silence a warning.

If genuinely obsolete or redundant, explain why and obtain approval
before removal.

Fix invalid hook usage, missing dependencies, unhandled promises,
unreachable code, unsafe assertions, missing return paths, resource
leaks, and incomplete error handling.

Do not use blanket eslint-disable, @ts-ignore, @ts-nocheck, underscore
renaming, dummy console.log statements, or artificial expressions to
hide warnings.

Do not weaken lint rules or tests just to obtain a clean report.

Use actual scripts configured in each service; do not assume all
directories use the same package manager.

The final report must include file/line, diagnostic, root cause,
intended functionality, implemented correction, tests performed, and
final status for material issues.
